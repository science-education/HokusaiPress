# 閲覧・書庫・学習ループ計画（ビューア方式の判断と実装分担）

状態: 計画確定（2026-07-01）。実装は Phase 0 から。
目的: 紙書籍を「コンピュータ上で活用できる環境」にする。検索可能PDFは一出力に過ぎない。
ScanTailor+Calibre 的価値を、**全自動整形＋閲覧時の誤り発見＋修正の学習・波及**で置き換える。

## 0. ビューア方式の判断

3案を比較した結論: **webui 拡張を本線**とし、pdf2clipboard からは**技術を移植**（コードベース統合はしない）、
**Calibre プラグインは作らない**（代わりに Calibre が取り込める出力を保証する疎結合）。

| 案 | 評価 | 理由 |
|---|---|---|
| A: pdf2clipboard (Rust/egui) を拡張 | ✗ 本線にしない | ビューアの存在理由は「閲覧中の誤り報告 → decisions 還流 → 再レンダ」であり、store.py/pipeline との密結合が本質。Python 側と二重管理になる。egui で領域編集レビューUIを再構築するコストも大。単一 main.rs 86KB は複数エージェント分担にも不向き |
| B: Calibre プラグイン | ✗ 作らない | Calibre 内蔵 Python/Qt 環境は制約が強くエージェント実装・反復検証に不向き。ビューア API も限定的で、修正フィードバックループが Calibre 側 DB と二重になる。書庫価値は FTS5 で安価に自前化できる |
| C: webui を「読むUI」に育てる | ✅ 採用 | queue→decide→log→rebuild のデータフローが既に実装・テスト済み。store 直結。Web スタックは Codex/Antigravity が最も高品質に書ける領域 |

### pdf2clipboard から移植する技術資産（コードでなく設計知見）
Web 版 pdf2clipboard は PDF.js ベースなので、webui ビューアへ直接知見が移る:
1. **世代管理による競合防止** — 読込/レンダ/操作が重なっても古い非同期結果が新状態を上書きしない。
2. **PDF.js の日本語対策** — CMap・標準フォントデータの明示指定で CID フォントの文字欠けを防ぐ。
3. **レンダリング並列度制御** — 環境に応じた同時実行数、タイムアウト、ページリソース解放、キャンセル。
4. **メモリ応答型の自動初期化** — 端末メモリを見てサムネイル解像度を初期化。
5. **サムネイル UX** — 中央基準ズーム、行中央寄せ、アニメ省略の瞬時スクロール、1秒フェードの軽い選択枠。
- 将来オプション（ストレッチ）: pdf_oxide の wasm ビルドをページグリッド部品として埋め込む。本計画の必須要素ではない。

### Calibre との関係（プラグインの代わり）
- 出力 PDF は既に PageLabels/ViewerPreferences を持つ。加えて **OPF（書誌メタデータ）を同梱出力**し、
  Calibre の「フォルダから追加」で書誌ごと取り込めるようにする。Calibre 併用ユーザーはそのまま恩恵。
- HokusaiPress 自身の書庫（FTS5 全文検索＋書誌）はこれと独立に持つ。OCR 本文の検索は
  PARAM_PROFILE_PLAN の著作権セーフ方針と分離: **検索索引はローカル DB のみ・共有対象外**。

## 1. アーキテクチャ（レイヤ）

```
[A] 補正パイプライン (既存)   — 全工程が confidence を出す
[B] 学習コア (拡張)          — decisions → 決定タイプ別学習器 (learn.py の一般化)
[C] 波及エンジン (新規)       — 修正 → 類似ページ kNN → 一括提案/自動適用
[D] 能動学習キュー (新規)     — 不確実性 × 解決される類似ページ数 × 重要度 で順位付け
[E] 書庫レイヤ (新規)         — documents 書誌 + FTS5 全文検索 + タグ
[F] 閲覧=レビューUI (統合)    — webui を読書UIへ。「このページ変」ワンタップ → decisions
[G] 高速化 (別線)            — docs/NPU_PARALLEL_PLAN.md に従う。本計画の範囲外
```

原則（不変条件）: **PageParams ストア + 純関数レンダラ**を崩さない。修正=パラメータ編集=安価な再レンダ。
learn.py の哲学を維持: モデルは可読 JSON、データ不足なら規則ベースへフォールバック、無言の誤りを出さない。

## 3. 実装分担とエージェント運用

役割: **Claude = spec 確定・契約（テスト）作成・統合レビュー・delicate な store/pipeline 統合**。
**Codex = バックエンド純ロジック**（テスト駆動が効く領域）。**Antigravity = webui フロントエンド**
（ブラウザ検証との相性が良い領域）。

### Antigravity の能力を引き出す工夫（重要）
Antigravity は自由度の高い依頼で迷走しやすい。以下を各 WP 依頼文の定型とする:

1. **設計判断を渡さない** — 判断は本文書と契約で確定済み。依頼文には「何を作るか」だけを書き、
   「どう設計すべきか」を考えさせない。選択肢を残すと脱線する。
2. **契約先渡し** — Claude が型シグネチャ・API スキーマ・受け入れテスト（pytest）を先に書いて
   リポジトリに置き、「このテストを green にせよ」を課題文にする。
3. **模倣対象の明示** — 「webui/app.py の Decision/RegionEdit の流儀で」「learn.py のフォールバック哲学で」
   と既存ファイルを指名。ゼロから様式を発明させない。
4. **1 WP = 1 ファイル中心 + 触ってよいファイル/触ってはならないファイルの列挙**（store.py と model.py は
   常に変更禁止リストに入れ、必要なら契約変更として Claude に差し戻させる）。
5. **検証コマンドを依頼文に埋める** — `python -m pytest tests/test_XX.py -q` と起動確認手順。
   green の証拠（テスト出力の貼付）を完了条件にする。
6. **DoD に HANDOFF.md 追記を含める**（何をどこに作ったか3行）。
7. **失敗時は依頼を直さず契約を直す** — 迷走したら依頼文を長くするのでなく、テストを追加して
   曖昧さを潰してから再依頼する。

Codex にも 2,5,6 は適用（1,3,4 は Codex では緩めてよい。設計余地への耐性が高い）。

## 4. リスクとガード
- **読まれないページの誤りは発見されない** → 低確信マーカー（WP-12）で受動レビューを誘発。
  加えて WP-31 のキューが能動的に拾う。二重化。
- **FTS5 索引と著作権セーフ共有の混同** → 索引はローカル `hokusai.db` のみ。bucket/prior 共有系
  （PARAM_PROFILE_PLAN §2）に本文テキストを載せない不変条件を test で固定。
- **波及の自動適用が誤爆** → learn.py と同じ確信マージンゲート＋`decided_by` で人手優先。
  自動適用は必ず decisions にログし、UI から一括取り消し可能にする。
- **エージェント成果物の品質分散** → 契約テスト先渡し＋Claude 統合レビューで吸収。
  マージ基準は「全テスト green + 契約不変」のみ。主観レビューを挟まない。
- **スコープ膨張** → Phase 5 以降（学習拡張の先、ネット共有等）は本文書で凍結。追加はこの文書の改訂として行う。
