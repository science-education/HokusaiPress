## 2. 分かっている事実（実測）

**認識精度**（`C:\tmp\acc-bench`、正解付き14頁で2026-11-22に再計算。空白を除いた文字誤り率）

| エンジン | shinto（素直な縦書き） | chufu（難しい頁） |
|---|---|---|
| NDL（DEIM＋PARSeq） | 1.6% | 9.4% |
| hybrid CPU／NPU | 1.9%／2.0% | 9.7%／9.6% |
| YomiToku（読み順補正あり） | 1.6% | 9.8% |

→ **認識精度は3者でほぼ同じ**。差が出るのは、行の検出漏れ（hybridは行の脱落・縦中横の取りこぼしが典型）、読み順、速度、出力PDFの質。

**速度**（この機 Core Ultra 7 155U）: NDL CPU 約1.9〜3.7秒/頁、hybrid NPU 約2.3〜3秒/頁、hybrid CPU 約5.6〜8.4秒/頁、YomiToku フル 約20秒/頁、PaddleOCR-VL 約70秒/頁。NDLのDEIMはNPUに載らない。

**NDLの強み**: DEIMが17クラスのレイアウト（図・表・ノンブル・柱など）を出す。CC BY 4.0 で、成果物に非商用の制約がつかない。

**HokusaiPressの現状の不具合**（2026-11-22に確認）:
- `--no-ocr` だと内容枠の推定を誤り、表紙のタイトル文字を余白として白く塗ってしまう（`img20261121_0002` p1）。OCRを有効にすると正しく出る。
- 表紙の下端にある薄い出版社名（「ミネルヴァ書房」）が、内容枠の外として白く塗られる（`img20261121_0014` p1、ndlocr）。
- 灰色のグラデーションの見出し帯が、二値化で黒い粗い点の塊になる。白抜きの見出し文字が読みにくい（`img20261121_0014` p3・p4。残課題E「網掛け」と同種）。

## 3. 問題点（整理が必要な理由）

1. **同じ機能が3〜4か所に重複**: 検索可能PDFの文字層（hybrid `pdf_export.py`、HokusaiPress `pdf_export/`、NDL `searchable_pdf.py`）、二値化（ScanTailor、HokusaiPress `mrc.py`、hybrid `binarize`）、PDFの読み込み。
2. **入口が多く、手順が人の記憶頼み**: 元データ → 本文二値化 → OCR済、の流れを毎回思い出す必要がある（今回それが起きた）。
3. **Python環境が分かれている**: メインの3.14ではNPU／YomiTokuが動かない。実運用は `NDL-OCR-Lite-NPU\.venv-openvino`（3.12）を間借りしている。
4. **評価データと校正コードが揮発する場所にある**: `C:\tmp` や `dev\tmp` に置いたベンチ・校正スクリプトが消えている。
5. **ローカルのcheckoutが古いことに気づけない**: 今回、HokusaiPressのローカルが origin/main より9コミット遅れたまま使われていた。
6. **ライセンスが混在**: hybridの検出器（YomiToku）は非商用（CC BY-NC-SA）。既定エンジンがhybridのままだと、成果物すべてが非商用扱いになる。

## 4. 目標: HokusaiPress を唯一のアプリにする

新しいアプリは作らない。いちばん機能が多く、エンジンを差し替える仕組みもあるHokusaiPressに集約する。他のリポジトリは「部品の供給元」か「保存のみ」にする。

### 4.1 処理の流れ（1コマンドで完結）

```
元データPDF ──▶ 補正（傾き・余白・影・判型）──▶ 二値化／MRC ──▶ OCR ──▶ (任意) AI校正 ──▶ 出力
                                                                     ├ 本文二値化PDF（文字層なし）
                                                                     ├ OCR済PDF（同じ画像＋文字層）
                                                                     └ テキスト・JSON・判断ログ
```

- **既定のOCRエンジンをNDL（`--ocr-engine ndlocr`）に変える**。精度は同等で、CPUで最速。レイアウト分類も使え、ライセンスもきれい。hybrid（NPU）は「速度優先」の選択肢として残し、PaddleOCR-VLは難しい頁だけの選択肢にする。
- **段階ごとの成果物を一度に出す**（`--emit binarized,ocr`）。今の「本文二値化」「OCR済」のフォルダ運用をそのまま再現する。
- **OCRだけをやり直すモード**（`hokusai-press ocr <pdf>`）。補正済みのPDFの画像をそのまま残し、文字層だけを付け替える（今回NDLに追加した重ね方式と同じ）。既存の63冊を、劣化させずにNDLでOCRし直すこともできる。
- **ファイル名に処理の印を付ける**（例 `_HP`）。あわせて、奥付・標題紙のOCRからNDL書誌を引いて書名に改名する機能を付ける（Hondanaで実績のある方法）。

### 4.2 部品の一本化

| 機能 | 残すもの | 片付けるもの |
|---|---|---|
| 文字層の書き込み | 1つのモジュールにまとめる（NDL `searchable_pdf.py` の重ね方式に、hybridのフォントフォールバック・互換漢字の畳み込みを統合） | hybrid・HokusaiPress の重複コード |
| 画像の符号化 | HokusaiPress の MRC（G4／JBIG2＋JPEG） | hybrid の `encode_page_pdf` |
| 二値化 | HokusaiPress `binarize_bw`（Otsu＋裏移りの2信号判定） | hybrid の `binarize`（OCR入力用にだけ残す） |
| NDLエンジン | NDL-OCR-Lite-NPU をパッケージとして依存利用 | — |
| AI校正 | 3者判定の手順を `hokusai_press/proof/` に作り直す（任意の工程） | 消えた gcheck |

### 4.3 環境・運用

- 実行用venvを1つにする: HokusaiPress専用の Python 3.12 venv（OpenVINO／NDL／hybridを同居）。`NDL-OCR-Lite-NPU` の venv の間借りをやめる。
- 起動時に、ローカルが origin より古ければ警告する（`hokusai-press doctor`）。
- 評価セット（正解付き頁）をリポジトリ内の `bench/` に移し、エンジンごとの誤り率・検出漏れ率を1コマンドで出す。CIでは数頁だけ回帰テストする。
- 長時間バッチは切り離したプロセスとログで回す（今回の `run_hp.ps1` の形）。中断した冊から再開できるようにする（出力済みはスキップ）。

### 4.4 保存のみにするもの

- **ScanTailorAdvancedTATEGAKI**: HokusaiPressの自動補正で品質が足りない本の「手動の逃げ道」として残す。新機能は入れない。
- **Yomitoku_NDL-OCR-Lite**: hybridエンジンの供給元として維持。PDF出力の開発はやめる。
- **ndlocr-lite-web-ai**: 単発の画像をブラウザで読む用途として残す（書籍の一括処理はしない）。
- `HokusaiPress-ocr-paddle` の worktree と `HokusaiPress_review` クローンは削除してよい（確認のうえ）。

## 5. 段階計画

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| 0 準備 | 専用venv、`doctor`、bench をリポジトリへ移す、NDL `feat/searchable-pdf` をpush・マージ | `bench` でNDL／hybridの誤り率が上の表と同じ値で再現する |
| 1 NDLを既定に | `--ocr-engine ndlocr` をこの機で実測（速度・頁ごとの検出漏れ）。問題なければ既定にする | 新規18冊のうち3冊×30頁で目視確認し、表紙・目次・図版頁で文字が消えない |
| 2 `--no-ocr` の不具合と画質 | 内容枠の推定失敗を「全面−細い縁」へ倒す（残課題C）。薄い端の文字を内容枠に含める。グラデーション帯を写真（灰色）として扱う | `img20261121_0002` p1 の題字、`0014` p1 の出版社名が残る。`0014` p4 の見出し帯が灰色で出る。既存テストが緑 |
| 3 段階別出力とOCRだけのやり直し | `--emit`、`ocr` サブコマンド、文字層モジュールの統合 | 二値化PDFとOCR済PDFの画像がバイト単位で一致。古い文字層が残らない |
| 4 命名 | 印の付与、書誌からの書名への改名（候補を出し、人が確定） | 18冊で書名候補の正解率を記録 |
| 5 AI校正 | 3者判定を任意の工程として作り直す | 1冊で、採用・保留の件数と無作為抽出の目視の正解率を記録 |
| 6 片付け | 重複コードの削除、保存のみのリポジトリのREADMEに「保存のみ」と明記 | 各リポジトリのREADMEから、どこを使えばよいかが一目で分かる |

各段階は、成果物の中身（画素・抽出したテキスト）で確かめる。テストが緑、という自己申告だけで完了にしない。

## 6. 進み具合

- 2026-11-22 方針決定: 統合先は HokusaiPress、既定のOCRは NDL。
- 段階0: NDL-OCR-Lite-NPU の `--pdf` をマージ（science-education/NDL-OCR-Lite-NPU#2）。`bench/ocr_bench.py` を追加。データは `C:\Users\user\dev\ocr-bench-data`（著作物のためリポジトリ外）。HokusaiPress のエンジン経由で、上の表の値が再現した。
- 段階1: `--ocr-engine` の既定を `ndlocr` に変更。新規18冊のうち3冊×30頁（0002・0009・0014）で、表紙・目次・図版・横書きの頁を目視確認した。OCRが原因で文字が消えた頁は無い。画像処理側の課題を2つ見つけた（2章の不具合の2・3点目）。
- 段階2（一部）: 内容枠を「検出領域の外接枠」だけで決めていたため、検出されない本物の文字が白く塗られていた。文字らしい墨のまとまり（3字以上・縁に接しない・細長い線でない）を内容枠に足すようにした（`margin.ink_text_clusters`）。`run` 経路で、`0002` の `--no-ocr` 表紙の題字、`0014` 表紙の出版社名、`0014` 中扉のロゴ上端が残ることを確認。ほかの頁は変化なし。グラデーション帯の件は未着手。
- 段階3: 文字層の書き込みを `hokusai_press/textlayer.py` に一本化（字ごとのフォント補い・互換漢字の畳み込み・既存文字層の除去・元PDFへの重ね書き）。`run` に `--suffix`・`--image-only-out`・`--skip-existing` を、新しく `ocr` サブコマンドを追加。実データで、ScanTailor 出力10頁の `ocr`（画像は元と同一、文字枠が各行に一致）と、`run` の2つの版の画像の一致を確認。
- 新たに見つけた不具合: `remargin`（OCRなしで余白だけ再計算）の結果が `run` と食い違う。`0014` の p8・p9 で、切り抜きが上に約1000〜2000px ずれ、本文が頁の下端に寄る。今回の修正とは無関係（修正を外しても同じ）。
- 余白処理の改良（margin v2、2026-11-22）: 18冊で旧方式の失敗を調べ、ScanTailor（内容枠）・同 TATEGAKI 版（ノンブルの合意位置）・unpaper・頁枠検出の方式と比べて作り直した。
  - 失敗の原因1: 内容枠がOCR領域と文字のまとまりだけで、黒地のノンブル・罫線・柱の一部などが白く塗られていた（`0012` p7）。→ 墨はすべて内容とし、紙の縁に接するもの・縁の帯のごみ・孤立した点だけを除く（`margin.content_ink_box`）。`ink_text_clusters` と `body_text_box` は廃止。
  - 失敗の原因2: 頁の位置をノンブルに合わせていたが、点や柱の漢字を頁番号と取り違えていた（`0010` p128 は4pxの点を「9」と読んだ）。誤った基準で頁が端に寄り、はみ出た部分が白く塗られた。→ 版面の書き出しの角（縦書きは右上、横書きは左上）に合わせる。本ごと・向きごと・奇偶ごとの合意位置から0.2in以内の頁だけをそろえ、ほかの頁（表紙・扉・図版）は紙の上での比率の位置を保つ。判型は版面と本の余白の中央値で決め、左右の余白は等しくする。
  - 失敗の原因3: 影の除去が「縁から15%以内の細長い成分」を影としていて、見出しの帯・柱の下の罫線・表の上枠・黒地の白抜き帯を消していた。9冊で測ると本物の影はすべて縁から1.3%以内で始まる。→ 3%以内に限った。
  - 内容に合わせて縮小した頁: 64頁→14頁（18冊・4,184頁）。各冊30頁を旧方式・新方式・余白なしで並べて目視確認した（`C:\tmp\hp1121\margin_eval\cmp_v4_*.png`）。
  - 残る課題: 小口の端に印刷された爪見出し（`0017` p129〜）は紙の縁に接するため消える（旧方式も同じ）。グラデーションの見出し帯の二値化（`0014`）は余白とは別の問題。
  - `remargin` が横向きの頁を回し直していなかった不具合も直した（`run` との食い違いの一因）。
- 頁の向き（2026-11-22）: 本と縦横が違う頁を一律に時計回りへ90°回していたが、`0010`・`0013` の該当12頁はすべて、黒い章扉の紙の大きさをスキャナーが検出できず、灰色の台ごと横長に保存されたもので、向きは正しかった。回したせいで横倒しになり、63%に縮小されていた（フォルダの `0010` にも横倒しの頁があった）。
  - 縦横が本と違う頁は、まず台を切り落とす（`source.find_paper`。両側の同じ灰色の均一な帯）。それで本と同じ向きなら回さない。
  - それでも違う頁だけ、行の揃い方（行頭がそろう・段落の最後の行が短い・段落頭の1字下げ）で正しい向きを選んで回す（`orientation.choose_rotation`）。20冊の20頁を左右に倒した40通りで全問正解。文字の中身（かなの数・よく使う語）での判定は、NDLが逆さの縦書きももっともらしく読むため使えなかった。
  - 切り抜きと回転は `SourceRef.paper`・`rotate` に記録し、`rebuild`・`remargin`・レビュー画面でも同じに適用する。`run --keep-orientation` で回さない。
  - `0010`・`0013` を処理し直し、フォルダの2冊（余白なし版）を差し替えた。章扉は縦長で前後の頁と同じ大きさになった。
- 斜めスキャンと黒い章扉（2026-11-23）:
  - `0010` p243・244 は約6°斜めに置かれた紙なのに、傾き補正が0°を返していた（信頼度は9.3・7.6と高く、要確認にもならなかった）。原因: 紙の四隅に写った灰色の台が二値化でインク扱いになり、台とスキャナーの白い縁取りの境目（画像の軸にぴったり沿う直線）が本文より強く効いた。本文が短く、角が折れて台が広く見えるほど起こる。→ 台を白くしてから推定する（`source.scanner_bed_mask`・`margin.whiten_scanner_bed`）。台は「台の明るさ・画像の縁につながる・7×7のばらつきが2以下（台は0.3〜0.8、印刷の灰色や紙は4〜29）・四辺に細い白い縁取りがある」ものだけ。紙の縁の影もたどって消す。4,184頁中で効くのは4頁だけ。p243・244 は 6.4°・−6.45° に直り、OCRの崩れ（「( ) ( 1 )…」など）も直った。
  - 試して採らなかった方法: 台を白い縁取りまで伸ばす（印刷が紙に対して少し傾いた頁で紙の縁に引っ張られた。`0002` p269 は 0.65°→−0.10°）。採点を縦横の「大きい方」から「合計」に変える（292頁が変わり、平均ではわずかに良いが悪化も85頁）。
  - `0014` p274 が0°のままだったのはスキャナ筋（センサー・ガラスの汚れで、紙送り方向に読み取り範囲の端から端まで出る線）のため。筋を消すと 6.2° に正しく補正される（文字だけの推定 6.35°）。筋は直さず警告する（下記）。
